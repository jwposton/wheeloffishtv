## Phase Goal

**As a** self-host operator, **I want to** configure named playlists with per-series ordered/disordered modes and episode count N, **so that** the nightly builder can generate deterministic mixed-TV output without DB or API coupling (Phase 5 orchestrates persistence).

<objective>
Wave 1 — Implement completion-event detection and policy resolution. Outputs a `RowBuildOutcome` per row that the Wave 3 builder consumes to filter active rows and override `effective_mode` before slot allocation.

Purpose: Lock policy semantics (`remove` | `restart` | `disordered`) for PLT-06. Centralize series-complete detection through `ResumeService` so builder + `/resume` endpoint never drift (Pitfall 1). Add the per-Playlist default policy field (D-13) needed by Phase 5 row creation; per-row override (D-14) is already structurally present from 04-01 — this plan locks the resolution rule.
Output: `core/playlist/completion.py`, expanded `domain/playlist.py`, tests for D-11, D-12, D-14, D-15.
</objective>

- D-12: system default policy is `REMOVE` — the Playlist `default_completion_policy` field defaults to `REMOVE` and PlaylistSeriesRow rows already default to `REMOVE` (set in 04-01).
- D-13: per-playlist default applies when Phase 5 creates new rows; Phase 4 only exposes the field. No mutation logic needed in this plan.
- D-14: per-row policy ALWAYS wins. `resolve_row_policy(playlist, row)` returns `row.completion_policy` unconditionally — the playlist default is reference data only.
- D-15: completion evaluated at start of build, before slot allocation. Phase 4 functions are stateless; the build pipeline (04-06) calls them exactly once per row.
- D-17 (RESTART semantics): the cursor reset to index 0 happens in the ordered picker (04-04) when it sees `policy_applied == RESTART`. This plan only sets the flag.
</locked_assumptions>

Implementation rules:
